OBJECTIVE

This document defines the mandatory execution sequence of the Knowledge Base.

It does not define Requirements, Criteria, Nonconformities or Report rules.

Its only purpose is to define the execution order.

###############################################################################
# EXECUTION CONTRACT
###############################################################################

The executor acts exclusively as the execution engine of the Knowledge Base.

The executor shall not:

- create Requirements;
- create Criteria;
- create Nonconformities;
- create documentary evidence;
- create technical conclusions;
- reinterpret the Knowledge Base;
- use external knowledge;
- modify execution results.

Every output shall originate exclusively from the active Knowledge Base.

###############################################################################
# EXECUTION SEQUENCE
###############################################################################

Execute the following phases exactly in this order.

Do not skip phases.

Do not change the execution order.

###############################################################################
# PHASE 1
# LOAD
###############################################################################

Load the active Knowledge Base.

Load:

00_engine

01_entities

02_requirements

02a_applicability

03_table1

04_table4

05_nonconformities

06_reports

09_Especificacao_da_RDE.txt (Documento 09-RDE)

08_execution_pipeline.txt is the current structural document containing this
manifest and completes the ten-document loaded set.

If any document is unavailable:

STOP EXECUTION.

Before normative execution, compare the loaded filenames and their
DOCUMENT_VERSION metadata with DOCUMENT_SET. In audit/debug mode, expose
KNOWLEDGE_BASE_ID, KNOWLEDGE_BASE_VERSION, SOURCE_COMMIT and every loaded
DOCUMENT_VERSION.

When the loaded identity metadata provides sufficient evidence of a missing,
extra or version-incompatible document, state the identity incompatibility
clearly in the existing audit/debug channel. Do not silently reconstruct the
expected release. This descriptive audit finding is not a new Engine state and
shall never create or modify PASS, FAIL, NOT_APPLICABLE, MANUAL_REVIEW,
EXECUTION_INTEGRITY_ERROR, a Nonconformity or an IRV/e-SCI pending entry.

###############################################################################
# PHASE 2
# DOCUMENT EXTRACTION
###############################################################################

The exclusive purpose of this phase is to construct the
Representação Documental Estruturada (RDE).

The RDE shall be constructed exactly as specified by:

09_Especificacao_da_RDE.txt (Documento 09-RDE).

Every extracted documentary fact shall be represented using the canonical representation defined by the RDE specification.

This phase shall never perform execution.

Do not:

- evaluate Requirements;
- evaluate Criteria;
- determine compliance;
- determine noncompliance;
- determine applicability;
- generate Nonconformities;
- generate operational alerts;
- generate technical conclusions.

###############################################################################
# DOCUMENT STATE
###############################################################################

For each document required by the active Knowledge Base, determine exactly one documentary state:

PRESENT

ABSENT

INCOMPLETE

UNVERIFIABLE

Store the documentary state for later execution.

###############################################################################
# DOCUMENTARY EXTRACTION
###############################################################################

Extract documentary information exactly as documented.

Do not reinterpret documentary content.

Do not classify documentary relevance.

Do not determine whether documentary information satisfies any Requirement.

Do not determine whether documentary information creates any Nonconformity.

Do not determine whether documentary information requires MANUAL_REVIEW.

Do not generate execution results from documentary content.

Documentary statements contained in submitted documents are not execution results.

They are only documentary evidence.

For COMPROVANTE_DE_SOLICITACAO_DE_HABITESE, identified only when the presented
document type is exactly "COMPROVANTE DE SOLICITAÇÃO DE HABITE-SE", extract
fact-only the documentally verifiable REQUEST_IDENTIFIER, PROCESS_IDENTIFIER
and PROTOCOL_IDENTIFIER; the
section SISTEMAS_E_MEDIDAS_DE_SEGURANCA and its directly verifiable
STRUCTURALLY_COMPLETE, LEGIBLE and VERIFIABLE properties; and each item
OFFICIAL_ESCI_CODE,
PRESENTED_SYSTEM_MEASURE_DESCRIPTION, RPCI_ORIENTATIVE_TEXT and SOURCE_LOCATION.
source_document remains required by Documento 09-RDE. The RPCI orientative-text
column is extracted as raw documentary text and is excluded from applicability.
This uses the schema in 01_entities and does not alter Documento 09-RDE.

###############################################################################
# ATTRIBUTE EXTRACTION
###############################################################################

Extract documentary attributes required by the active Knowledge Base.

- SIGNED
- APPROVED
- PAID
- RT_NAME
- RI_NAME
- ADDRESS
- AREA

- IDENTIFIERS

When evaluating SIGNED:

Search only for documentally verifiable digital or electronic signatures.

When no documentally verifiable digital or electronic signature can be confirmed,

leave the SIGNED attribute empty in the RDE.

Do not store SIGNED = FALSE or an execution state such as MANUAL_REVIEW during
EXTRACTION.

No documentary attribute may be inferred from another documentary attribute.

Every stored attribute shall be directly supported by documentary evidence contained in the administrative process.

###############################################################################
# EXECUTION BOUNDARY
###############################################################################

No documentary statement may influence the execution directly.

Every SMSCI-scoped execution result shall originate exclusively from the
following execution chain:

Process Memory

↓

Applicability Rule

↓

PROCESS.SMSCI

↓

Requirement

↓

Criterion

↓

Execution Result

↓

Nonconformity (when FAIL)

- MANUAL_REVIEW
- NOT_APPLICABLE
- Nonconformity
- Operational Alert

Document extraction is complete only after every submitted document has been processed.

END PHASE 2.

###############################################################################
# PHASE 3
# ENTITY NORMALIZATION AND PROCESS MEMORY
###############################################################################

Consume only the completed, immutable RDE.

Normalize representations derived from the RDE using 01_entities.

For every comprovante section represented in the RDE, normalize an exact
OFFICIAL_ESCI_CODE only through the authorized OFFICIAL_ESCI_CODE -> canonical
entity combination declared in 02a_applicability. Do not select the current
comprovante in this phase. Preserve AI and DAI as distinct documentary facts;
do not normalize either into SMSCI_SDAI. Alias normalization does not create an
applicability decision.

Do not alter, add, remove or reinterpret any RDE record.

Merge equivalent entities only in the derived normalized representation.

Preserve every reference to the original RDE record and Source Document.

No inference is allowed.

Build Process Memory exclusively from the normalized representation derived
from the immutable RDE.

The RDE is the only documentary input authorized for Process Memory
construction.

Process Memory shall never:

- create or reinterpret documentary facts;
- determine applicability;
- evaluate Requirements;
- evaluate Criteria;
- generate execution results;
- generate Nonconformities.

Close Process Memory as complete and immutable before Phase 4.

Requirements, Criteria and Report generation shall consume Process Memory only.

Do not reopen Source Documents or retry documentary extraction in this or any
later phase.

END PHASE 3.

###############################################################################
# PHASE 4A
# SMSCI APPLICABILITY RESOLUTION
###############################################################################

Apply 02a_applicability only after Process Memory is complete and immutable.

Select exactly one current comprovante by the deterministic identifier contract
declared in 02a_applicability. All comparable request, process and protocol
identifiers shall agree. Do not select by filename, date or attachment order.

Derive productive targets only from canonical entities declared with
APPLICABILITY_TARGET_CLASS OFFICIAL_ESCI_SCOPE in 01_entities. Resolve their
exact official code only through the authorized document, section and mapping
declared in 02a_applicability. Validate that Requirement SMSCI and Criterion
APPLIES_TO references resolve to canonical entities with their declared target
class.

Evaluate only complete declared applicability rules against authorized,
traceable Process Memory facts.

Alias normalization, textual occurrence, detected entities, document
existence, RPCI orientative text, GLP_MASS_KG and SMSCI metadata on a report,
manual, laudo, DRT or other document required by the target shall never
activate that target.

Every target shall receive an explicit, deterministic and traceable positive
or negative decision before PROCESS.SMSCI is released.

If the selected document is absent or not identified, its section is absent,
incomplete, illegible or unverifiable, its exact code is unknown, a required
fact is absent, a decision conflicts, or traceability is incomplete:

STOP APPLICABILITY RESOLUTION BEFORE THE ENGINE.

Do not emit a partial PROCESS.SMSCI.

Do not create a Criterion result or convert the indeterminacy to
NOT_APPLICABLE, MANUAL_REVIEW, UNKNOWN or FAIL.

END PHASE 4A.

###############################################################################
# PHASE 4B
# REQUIREMENT APPLICABILITY RESOLUTION
###############################################################################

Only after Phase 4A completes, determine APPLICABLE_REQUIREMENTS from the
resolved PROCESS.SMSCI and existing Requirement metadata.

Requirements without SMSCI metadata retain their declared applicability
semantics and shall not be filtered through PROCESS.SMSCI.

Requirements with SMSCI metadata are applicable only when their declared
target is present in PROCESS.SMSCI.

Iterative Requirements retain their declared form.

WORKLIST.SMSCI is a transient iteration view derived only from
PROCESS.SMSCI. It shall always be a subset of PROCESS.SMSCI and shall never
discover an SMSCI.

For REQ_T1_DRT_SMSCI / T1_DRT_SMSCI_COVERAGE, WORKLIST.SMSCI projects every
and only positive OFFICIAL_ESCI_SCOPE target in PROCESS.SMSCI. It excludes
DERIVED_INTERNAL_REQUIREMENT_SCOPE targets, including SMSCI_SDAI, and this
does not establish a general architectural identity between WORKLIST.SMSCI and
PROCESS.SMSCI.

No Requirement may be created or rewritten.

END PHASE 4B.

###############################################################################
# PHASE 4C
# CRITERION SELECTION
###############################################################################

Materialize the ordered, closed and immutable list PLANNED_EXECUTION_UNITS
exclusively through the declared USES or REQUIREMENT associations of
APPLICABLE_REQUIREMENTS. Do not execute any Criterion while constructing it.

Preserve declared file order, TABLE and CONTEXT.

Do not create a Criterion or select one by alias, document, similarity or
textual occurrence.

APPLIES_TO shall be consistent with the completely resolved PROCESS.SMSCI.
Any inconsistency shall stop execution before the Engine.

Retain every VALIDATE declared by APPLICABLE_REQUIREMENTS in the execution
plan.

Validate the existing Criterion and Nonconformity references without creating
or triggering a Nonconformity.

END PHASE 4C.

Each PLANNED_EXECUTION_UNIT shall contain, at minimum:

- UNIT_KEY = (requirement_id, criterion_id);
- a reference to the already resolved Applicability;
- no documentary evidence copied from the Process Memory;
- no execution result;
- no anticipated Nonconformity.

The plan shall consume the already resolved Applicability; it shall not
recalculate, reinterpret or modify Applicability.

The list shall be frozen before Table 1 execution and remain frozen through
Table 4 execution. It shall contain all and only the Criteria declared for
each applicable Requirement, exactly once.

The following Base-to-Plan invariant is mandatory:

- every applicable Requirement shall have all its declared Criteria represented;
- no applicable Requirement may be left without its planned Criteria;
- no Criterion outside the resolved Applicability may enter the list;
- no UNIT_KEY may occur more than once.

For an iterative Criterion, PLANNED_EXECUTION_UNITS shall contain one unit for
the Criterion, not one unit per binding. The unit shall contain a separately
frozen ITERATION_DOMAIN describing the planned bindings.

ITERATION_DOMAIN defines the complete planned_bindings set.

planned_bindings = ITERATION_DOMAIN

FOR_EACH remains an internal operation of that Criterion and preserves its
aggregate result semantics. In particular, T1_DRT_SMSCI_COVERAGE remains one
planned unit with multiple internal bindings and one aggregate result; it may
produce at most one NC_T1_002 when its declared Criterion result is FAIL.

No list parallel to PLANNED_EXECUTION_UNITS shall be introduced merely to
duplicate its expected, selected or executed Criteria.

END PLANNED_EXECUTION_UNITS CONSTRUCTION.

###############################################################################
# PHASE 5
# TABLE EXECUTION
###############################################################################

Consume only the immutable Process Memory, the completely resolved
PROCESS.SMSCI, APPLICABLE_REQUIREMENTS and PLANNED_EXECUTION_UNITS produced by
Phases 4A through 4C.

The Engine consumes PROCESS.SMSCI as already resolved and shall never create it
or modify it. The Engine shall never receive indeterminate or partial SMSCI
scope.

Execute all APPLICABLE_REQUIREMENTS using Process Memory.

Resolve every VALIDATE declared by each APPLICABLE_REQUIREMENT.

After Requirement validation, execute exactly the Criteria represented by
PLANNED_EXECUTION_UNITS, in the frozen plan order.

Execute Table 1.

Complete every applicable Criterion in Table 1 before starting Table 4.

Each selected Criterion shall produce exactly one result.

Every applicable Requirement shall be evaluated exactly once.

Every execution result shall record the UNIT_KEY of its planned unit.

For every iterative Criterion, record the bindings actually evaluated and
retain the planned ITERATION_DOMAIN. The execution shall verify:

evaluated_bindings == planned_bindings

before the results are consolidated or projected.

Allowed results:

PASS

FAIL

NOT_APPLICABLE

MANUAL_REVIEW

No other result is allowed.

Criteria shall consume Process Memory only.

Criteria shall never create, update or reinterpret documentary attributes.

###############################################################################
# PHASE 6
# RESULT CONSOLIDATION
###############################################################################

Before consolidation or projection, verify the Plan-to-Results invariant:

- every PLANNED_EXECUTION_UNITS UNIT_KEY produced exactly one result;
- no UNIT_KEY produced two or more results;
- no result exists without a UNIT_KEY in PLANNED_EXECUTION_UNITS;
- for every iterative Criterion, evaluated_bindings equals planned_bindings.

If any of these checks fails, stop execution with EXECUTION_INTEGRITY_ERROR.

EXECUTION_INTEGRITY_ERROR is an internal execution error only. It is not a
normative result and shall never be treated as:

PASS, FAIL, NOT_APPLICABLE, MANUAL_REVIEW, UNKNOWN or Nonconformity.

On EXECUTION_INTEGRITY_ERROR:

- stop before IRV/e-SCI projection;
- do not generate a pendency;
- do not alter normative results;
- do not convert the error to MANUAL_REVIEW;
- expose it only through the existing audit/debug channel when supported by the
  architecture;
- do not trigger Report Generation or IRV/e-SCI projection.

Consolidate all Criterion results.

Associate Nonconformities only with FAIL results.

Criterion results shall remain immutable after consolidation.

Associate operational alerts only with MANUAL_REVIEW results.

Operational Alerts are internal execution artifacts.

Before Report Generation,

every Operational Alert shall be translated into exactly one
MANUAL_REVIEW report entry.

Operational Alert identifiers shall never appear in user-visible reports.

MANUAL_REVIEW results shall never generate Nonconformities.

MANUAL_REVIEW shall propagate to every dependent Criterion unless an explicit documentary rule defines otherwise.

Do not modify previous results.

No report section shall be generated before Result Consolidation completes.

###############################################################################
# PHASE 6A
# IRV OPERATIONAL PROJECTION
###############################################################################

Only after Result Consolidation completes, consume the immutable consolidated
Criterion results and their declared Nonconformity associations.

For each consolidated FAIL associated with a Nonconformity that declares
IRV_TABLE, IRV_CRITERION and IRV_CAUSE in 05_nonconformities, create exactly
one transient operational pending-entry. Load IRV_SUBCAUSE only when declared;
the selectable leaf is IRV_SUBCAUSE when present, otherwise IRV_CAUSE. Preserve
IRV_CAUSE as the internal parent when a subcause is present. Preserve consolidated result order and the complete traceability of the source
FAIL and documentary evidence.

The operational projection is not a Criterion result, a Nonconformity or
documentary evidence. It shall never:

- create, remove, merge or modify a FAIL;
- create or modify a Nonconformity;
- execute a Requirement or Criterion;
- recalculate Applicability or PROCESS.SMSCI;
- reopen a Source Document or the RDE;
- infer an IRV item, cause or subcause by similarity;
- create an artificial IRV_SUBCAUSE.

Do not group, deduplicate or suppress pending entries because they share the
same IRV_CRITERION. Distinct selectable leaves — IRV_SUBCAUSE when declared,
otherwise IRV_CAUSE — shall remain distinct operational pending entries.

FOR_EACH is a structural aggregation inside one Criterion evaluation. Its
instances shall produce one consolidated Criterion result and, on FAIL, one
association with the declared Nonconformity. Repeated failing instances with
the same Nonconformity and the same selectable IRV leaf are evidence of that
single pending entry, not additional pending entries. Preserve and aggregate
their traceable evidence for a minimal DESCRIPTION when needed. This rule shall
never merge distinct Nonconformities or distinct selectable IRV leaves.

When a triggered Nonconformity has no declared IRV projection, preserve its
FAIL and route the missing operational projection to the report's human
treatment section. Do not invent an e-SCI item or cause and do not convert the
FAIL to MANUAL_REVIEW.

For DESCRIPTION_POLICY MINIMAL_IF_NEEDED, attach a DESCRIPTION only when a
concrete fact already present in the consolidated result and its evidence is
needed to identify the divergence. Simple documentary absence requires no
additional description. DESCRIPTION shall normally contain one sentence of no
more than 180 characters; 180 is a preference, not a validity limit. The
absolute limit is 500 characters. DESCRIPTION shall not reproduce the complete
IRV_CAUSE, IRV_SUBCAUSE or IRV_CRITERION. If no description is needed,
project exactly "Não necessário." for report rendering.

Derive candidate technical counters only from the canonical consolidated
result set before rendering. Validate:

VERIFICATIONS_EXECUTED = PASS + FAIL + NOT_APPLICABLE + MANUAL_REVIEW

If the equality is not satisfied, record REPORT_COUNTER_INCONSISTENCY as an
audit-only diagnostic and omit the invalid technical totals. Never fabricate,
adjust or reconstruct a counter from rendered text blocks. The inconsistency
shall not create or modify PASS, FAIL, NOT_APPLICABLE, MANUAL_REVIEW,
Nonconformities or operational pending entries. Continue operational report
generation when the canonical results and operational projection remain
intact; expose the inconsistency explicitly only in audit mode.

The transient operational projection becomes immutable before Phase 7.

END PHASE 6A.

###############################################################################
# PHASE 7
# REPORT GENERATION
###############################################################################

Generate the operational report using only the immutable consolidated results,
the immutable Phase 6A operational projection and 06_reports.

Do not expose Requirements, Criteria or internal identifiers in the
operational report.

The operational report shall not reinterpret execution results.

If the user explicitly requests any Technical Annex trigger declared by
06_reports, append the Technical Annex defined by that same document.

The Technical Annex shall describe only the execution actually performed by the inference engine.

The audit report shall not introduce new documentary findings after Result Consolidation.

###############################################################################
# EXECUTION RULES
###############################################################################

Never execute phases out of order.

Never return to a previous phase.

Never modify results produced in previous phases.

Never replace documentary evidence with model knowledge.

Never infer absent information.

When documentary evidence cannot be verified, return exactly:

Informação insuficiente para verificar.

The report generation phase shall never trigger additional documentary analysis.

If additional documentary evidence would be required to change a result, the execution shall terminate with the previously consolidated results.
