###############################################################################
# PHASE 3
# ENTITY NORMALIZATION AND IMMUTABLE EXECUTION VIEW (PROCESS MEMORY CONTRACT)
###############################################################################

Consume only the completed, immutable RDE.

Normalize representations derived from the RDE using 01_entities.

For every comprovante section represented in the RDE, normalize an exact
OFFICIAL_ESCI_CODE only through the authorized OFFICIAL_ESCI_CODE -> canonical
entity combination declared in 02a_applicability. Do not select the current
comprovante in this phase. Preserve AI and DAI as distinct documentary facts;
do not normalize either into SMSCI_SDAI. Alias normalization does not create an
applicability decision.

Do not alter, add, remove or reinterpret any RDE record.

Merge equivalent entities only in the derived normalized representation.

Preserve every reference to the original RDE record and Source Document.

No inference is allowed.

Provide an immutable execution view (the Process Memory contract) exclusively
from the normalized representation derived from the immutable RDE. This view
is a read-only execution contract, not a mandatory materialized or persisted
artifact. When no transformation is needed, a read-only adapter may expose the
validated RDE directly. When normalization is needed, it may exist in memory;
do not persist a second copy of the RDE solely to materialize Process Memory.

The RDE is the only documentary input authorized for the execution view. The
view or read-only adapter shall expose only approved execution interfaces,
canonicalized entities and attributes, TypedReference values when required,
and provenance back to the RDE and source records. Predicates shall not
navigate the raw RDE arbitrarily or bypass the closed Phase 3 view. The view
shall not reopen source documents, invoke extraction, or become a second
documentary source of truth.

Process Memory shall never:

- create or reinterpret documentary facts;
- determine applicability;
- evaluate Requirements;
- evaluate Criteria;
- generate execution results;
- generate Nonconformities.

Close Process Memory as complete and immutable before Phase 4. This closes the
logical execution view, whether backed by an adapter or an in-memory normalized
representation; it does not require persistence.

Requirements, Criteria and Report generation shall consume Process Memory only.

Do not reopen Source Documents or retry documentary extraction in this or any
later phase.

END PHASE 3.

###############################################################################
# PHASE 4A
# SMSCI APPLICABILITY RESOLUTION
###############################################################################

Apply 02a_applicability only after the Process Memory execution view is
complete and immutable.

Select exactly one current comprovante by comparing its PROTOCOL_IDENTIFIER and
canonical civil REQUEST_DATE with the immutable CurrentSubmissionContext
provided by operational intake, as declared in 02a_applicability. A different
request date under the same protocol denotes another presentation. RE_IDENTIFIER
is only a consistency check when available on both sides. processId and
REQUEST_IDENTIFIER do not participate. Do not select by filename, generated or
created timestamp, hash, record_id, attachment count or order. The context is
operational metadata outside the RDE and must be complete, traceable and frozen
before this phase.

Derive productive targets only from canonical entities declared with
APPLICABILITY_TARGET_CLASS OFFICIAL_ESCI_SCOPE in 01_entities. Resolve their
exact official code only through the authorized document, section and mapping
declared in 02a_applicability. Validate that Requirement SMSCI and Criterion
APPLIES_TO references resolve to canonical entities with their declared target
class.

Only after every official decision is complete, derive the internal scopes
declared in 02a_applicability. In particular, a negative SMSCI_IEL decision
from a complete, legible and verifiable official section shall derive only
SMSCI_IN19_APPLICABILITY_REVIEW; it shall not create SMSCI_IEL or determine
whether IN19 applies or is dispensed. An incomplete, illegible or unverifiable
section remains an ARCHITECTURAL_BLOCKER before any derivation.

Evaluate only complete declared applicability rules against authorized,
traceable Process Memory facts.

Alias normalization, textual occurrence, detected entities, document
existence, RPCI orientative text, GLP_MASS_KG and SMSCI metadata on a report,
manual, laudo, DRT or other document required by the target shall never
activate that target.

Every target shall receive an explicit, deterministic and traceable positive
or negative decision before PROCESS.SMSCI is released.

If the selected document is absent or not identified, its section is absent,
incomplete, illegible or unverifiable, its exact code is unknown, a required
fact is absent, a decision conflicts, or traceability is incomplete:

STOP APPLICABILITY RESOLUTION BEFORE THE ENGINE.

Do not emit a partial PROCESS.SMSCI.

Do not create a Criterion result or convert the indeterminacy to
NOT_APPLICABLE, MANUAL_REVIEW, UNKNOWN or FAIL.

END PHASE 4A.

###############################################################################
# PHASE 4B
# REQUIREMENT APPLICABILITY RESOLUTION
###############################################################################

Only after Phase 4A completes, determine APPLICABLE_REQUIREMENTS from the
resolved PROCESS.SMSCI and existing Requirement metadata.

After an explicit positive SMSCI_IEL decision, resolve exactly one internal
IN19_DOCUMENTATION_REGIME from only the REQUEST_DATE extracted from the
selected comprovante: REQUEST_DATE <= 2024-04-24 is LEGACY; REQUEST_DATE >
2024-04-24 is CURRENT. The selected comprovante can only have a canonical
REQUEST_DATE equal to CurrentSubmissionContext.requestDate; missing, invalid,
unverifiable or non-comparable dates block during Phase 4A selection and never
reach this resolution. Do not use PPCI, ART/RRT/TRT, atestado, previsão, início,
conclusion date or textual mention of obra nova. SMSCI_IEL negative preserves
the declared IN19 applicability-review path and does not resolve a regime.

Requirements without SMSCI metadata retain their declared applicability
semantics and shall not be filtered through PROCESS.SMSCI.

Requirements with SMSCI metadata are applicable only when their declared
target is present in PROCESS.SMSCI.

For positive SMSCI_IEL, additionally select IN19 Requirements only when their
declared IN19_DOCUMENTATION_REGIME equals the resolved value: CURRENT selects
only REQ_IN19_EXECUTION, REQ_IN19_GROUNDING and REQ_IN19_FINAL_VERIFICATION;
LEGACY selects only REQ_IN19_LEGACY_DOCUMENTATION. UNRESOLVED,
REQ_IN19_REGIME_REVIEW and T4_IN19_REGIME_REVIEW are
LEGACY_REFERENCE / NOT_PRODUCTIVELY_REACHABLE under strict matching; they shall
not be selected or planned. A Criterion result, including UNKNOWN, shall never
resolve or reconstruct the regime.

Iterative Requirements retain their declared form.

WORKLIST.SMSCI is a transient iteration view derived only from
PROCESS.SMSCI. It shall always be a subset of PROCESS.SMSCI and shall never
discover an SMSCI.

For REQ_T1_DRT_SMSCI / T1_DRT_SMSCI_COVERAGE, WORKLIST.SMSCI projects every
and only positive OFFICIAL_ESCI_SCOPE target in PROCESS.SMSCI. It excludes
DERIVED_INTERNAL_REQUIREMENT_SCOPE targets, including SMSCI_SDAI and
SMSCI_IN19_APPLICABILITY_REVIEW, and this does not establish a general
architectural identity between WORKLIST.SMSCI and PROCESS.SMSCI.

No Requirement may be created or rewritten.

END PHASE 4B.

###############################################################################
# PHASE 4C
# PLAN MATERIALIZATION
###############################################################################

INPUT: APPLICABLE_REQUIREMENTS and the release-derived
COMPILED_EXECUTION_INDEX. Freeze APPLICABLE_REQUIREMENTS and consume it only;
do not recalculate, reinterpret or modify Applicability or
IN19_DOCUMENTATION_REGIME.

Materialize the ordered, closed and immutable PLANNED_EXECUTION_UNITS as a
local procedure:

1. For each applicable Requirement in its resolved order, find its block in
   COMPILED_EXECUTION_INDEX and copy every listed UNIT_KEY in that block order.
   UNIT_KEY shall be copied literally. Do not generate, rename, summarize or
   reinterpret it. Semantic labels are not valid substitutes.

2. Preserve the declared TABLE, CONTEXT and every VALIDATE associated with the
   copied Requirement and Criterion. APPLIES_TO shall be consistent with the
   completely resolved PROCESS.SMSCI; any inconsistency stops execution before
   the Engine.

3. When the Requirement block declares ITERATION_SOURCE, materialize one unit
   for each listed UNIT_KEY, resolve and freeze its ITERATION_DOMAIN from that
   ITERATION_SOURCE. Do not materialize a UNIT_KEY per binding.

4. Validate the existing Criterion and Nonconformity references without
   creating or triggering a Nonconformity. Do not execute a Criterion while
   constructing the plan.

5. Freeze PLANNED_EXECUTION_UNITS. Compare its ordered UNIT_KEY sequence for
   exact equality with the ordered sequence selected from
   COMPILED_EXECUTION_INDEX for the applicable Requirements. Any order change,
   absence, extra key or duplicate is EXECUTION_INTEGRITY_ERROR: STOP BEFORE
   EXECUTION.

Each PLANNED_EXECUTION_UNIT contains its literal UNIT_KEY and a reference to
the already resolved Applicability, but no documentary evidence copied from
Process Memory, execution result or anticipated Nonconformity.

ITERATION_DOMAIN defines the complete planned_bindings set. FOR_EACH remains
internal to the Criterion and preserves aggregate result semantics. In
particular, T1_DRT_SMSCI_COVERAGE remains one planned unit with multiple
internal bindings and one aggregate result; it may produce at most one
NC_T1_002 when its declared Criterion result is FAIL.

No list parallel to PLANNED_EXECUTION_UNITS shall be introduced merely to
duplicate its expected, selected or executed Criteria.

END PHASE 4C.

###############################################################################
# PHASE 5
# TABLE EXECUTION
###############################################################################

Consume only the immutable Process Memory, the completely resolved
PROCESS.SMSCI, APPLICABLE_REQUIREMENTS and PLANNED_EXECUTION_UNITS produced by
Phases 4A through 4C.

The Engine consumes PROCESS.SMSCI as already resolved and shall never create it
or modify it. The Engine shall never receive indeterminate or partial SMSCI
scope.

Execute all APPLICABLE_REQUIREMENTS using Process Memory.

Resolve every VALIDATE declared by each APPLICABLE_REQUIREMENT.

After Requirement validation, process exactly the Criteria represented by
PLANNED_EXECUTION_UNITS, in the frozen plan order. Before executing a
dependent Criterion, determine whether an earlier result requires
MANUAL_REVIEW propagation. If propagation applies, register the dependent unit
as PROPAGATED and do not execute its predicate or ASSERT. Otherwise register
the unit as EVALUATED and execute it.

Execute Table 1.

Complete every applicable Criterion in Table 1 before starting Table 4.

Each selected Criterion shall produce exactly one result record. Only an
EVALUATED record represents an executed Criterion; a PROPAGATED record
represents the frozen plan unit whose evaluation was intentionally skipped and
whose causal source is recorded.

Every applicable Requirement shall be evaluated exactly once.

Every result record shall record the UNIT_KEY of its planned unit and
`pipeline_result`. Only EVALUATED records shall contain `engine_result`,
`normalization`, predicate trace, evidence references and evaluated bindings of
their own.
PROPAGATED records shall contain the causal source and propagation cause
specified below, without fabricating those evaluation fields.

For every EVALUATED iterative Criterion, record the bindings actually evaluated
and retain the planned ITERATION_DOMAIN. The execution shall verify:

evaluated_bindings == planned_bindings

before the results are consolidated or projected.

The Engine preserves its internal EngineResult for every EVALUATED Criterion:

TRUE

FALSE

UNKNOWN

NOT_APPLICABLE

MANUAL_REVIEW

Normalize each EngineResult at the Engine/Pipeline boundary to exactly one
PipelineResult as follows:

| EngineResult | PipelineResult | Trace normalization |
| --- | --- | --- |
| TRUE | PASS | IDENTITY |
| FALSE | FAIL | IDENTITY |
| NOT_APPLICABLE | NOT_APPLICABLE | IDENTITY |
| MANUAL_REVIEW | MANUAL_REVIEW | IDENTITY |
| UNKNOWN | MANUAL_REVIEW | UNKNOWN_TO_MANUAL_REVIEW |

Every result record shall preserve `pipeline_result`. An EVALUATED result
shall additionally preserve its own `engine_result` and `normalization`, with
the predicate trace for that evaluation. A PROPAGATED result shall preserve
`pipeline_result=MANUAL_REVIEW` and a causal link sufficient to reconstruct
the originating EngineResult and normalization, without assigning those fields
to the dependent Criterion. UNKNOWN_TO_MANUAL_REVIEW is an operational routing
normalization only; it does not make UNKNOWN semantically identical to
MANUAL_REVIEW. It shall not generate FAIL or a Nonconformity, alter evidence,
or reinterpret documentary absence. Only EngineResult FALSE normalizes to
FAIL, and a Nonconformity is associated only when the Criterion declares one.

Allowed PipelineResults:

PASS

FAIL

NOT_APPLICABLE

MANUAL_REVIEW

No other PipelineResult is allowed. The EngineResult remains available in the
trace even when its PipelineResult is normalized.

Criteria shall consume Process Memory only.

Applicability remains resolved before execution. A predicate may return
NOT_APPLICABLE only when its declared result contract permits it; the Engine
shall not invent propagation or composition semantics for that state in ALL,
OR or FOR_EACH. An undeclared combination is an execution integrity error.

Criteria shall never create, update or reinterpret documentary attributes.

###############################################################################
# PHASE 6
# RESULT CONSOLIDATION
###############################################################################

Before consolidation or projection, verify the Plan-to-Results invariant:

- every PLANNED_EXECUTION_UNITS UNIT_KEY produced exactly one result record,
  evaluated or propagated;
- no UNIT_KEY produced two or more results;
- no result exists without a UNIT_KEY in PLANNED_EXECUTION_UNITS;
- for every EVALUATED iterative Criterion, evaluated_bindings equals
  planned_bindings; PROPAGATED records have no evaluated bindings.

If any of these checks fails, stop execution with EXECUTION_INTEGRITY_ERROR.

EXECUTION_INTEGRITY_ERROR is an internal execution error only. It is not a
normative result and shall never be treated as:

PASS, FAIL, NOT_APPLICABLE, MANUAL_REVIEW, UNKNOWN or Nonconformity.

On EXECUTION_INTEGRITY_ERROR:

- stop before IRV/e-SCI projection;
- do not generate a pendency;
- do not alter normative results;
- do not convert the error to MANUAL_REVIEW;
- expose it only through the existing audit/debug channel when supported by the
  architecture;
- do not trigger Report Generation or IRV/e-SCI projection.

Consolidate all Criterion results, preserving PipelineResult for every record
and preserving EngineResult and normalization on EVALUATED records. Propagated
records retain their causal source link instead of receiving an EngineResult
or normalization of their own.

This contract defines results per Criterion and does not define an aggregate
Requirement result. Do not derive or emit a Requirement-level result by
combining Criteria unless a separate canonical contract is approved.

Associate Nonconformities only with FAIL results.

Criterion results shall remain immutable after consolidation.

Associate operational alerts only with MANUAL_REVIEW results.

Operational Alerts are internal execution artifacts.

Before Report Generation,

every Operational Alert shall be translated into exactly one
MANUAL_REVIEW report entry.

Operational Alert identifiers shall never appear in user-visible reports.

MANUAL_REVIEW results shall never generate Nonconformities.

MANUAL_REVIEW shall propagate to every dependent Criterion unless an explicit documentary rule defines otherwise.

Propagation is represented explicitly. Every planned UNIT_KEY produces exactly
one result record with `result_origin` equal to `EVALUATED` or `PROPAGATED`.

An EVALUATED record represents a Criterion actually executed and shall contain
`evaluation_performed=true`, `engine_result`, `pipeline_result` and
`normalization`, plus the predicate trace and evidence references required by
the Criterion contract.

A PROPAGATED record represents a dependent Criterion that was not executed and
shall contain `evaluation_performed=false`, `source_unit` or
`source_criterion`, `propagation_cause` and `pipeline_result=MANUAL_REVIEW`.
It shall not fabricate an EngineResult for the dependent Criterion, predicate
bindings, predicate trace or evidence. The source link shall preserve the
causal chain, including `UNKNOWN -> UNKNOWN_TO_MANUAL_REVIEW -> MANUAL_REVIEW`
when that is the originating result. Propagation never produces FAIL,
Nonconformity, facts or altered evidence.

Do not modify previous results.

No report section shall be generated before Result Consolidation completes.

###############################################################################
# PHASE 6A
# IRV OPERATIONAL PROJECTION
###############################################################################

Only after Result Consolidation completes, consume the immutable consolidated
Criterion results and their declared Nonconformity associations.

For each consolidated FAIL associated with a Nonconformity that declares
IRV_TABLE, IRV_CRITERION and IRV_CAUSE in 05_nonconformities, create exactly
one transient operational pending-entry. Load IRV_SUBCAUSE only when declared;
the selectable leaf is IRV_SUBCAUSE when present, otherwise IRV_CAUSE. Preserve
IRV_CAUSE as the internal parent when a subcause is present. Preserve consolidated result order and the complete traceability of the source
FAIL and documentary evidence.

The operational projection is not a Criterion result, a Nonconformity or
documentary evidence. It shall never:

- create, remove, merge or modify a FAIL;
- create or modify a Nonconformity;
- execute a Requirement or Criterion;
- recalculate Applicability or PROCESS.SMSCI;
- reopen a Source Document or the RDE;
- infer an IRV item, cause or subcause by similarity;
- create an artificial IRV_SUBCAUSE.

Do not group, deduplicate or suppress pending entries because they share the
same IRV_CRITERION. Distinct selectable leaves — IRV_SUBCAUSE when declared,
otherwise IRV_CAUSE — shall remain distinct operational pending entries.

FOR_EACH is a structural aggregation inside one Criterion evaluation. Its
instances shall produce one consolidated Criterion result and, on FAIL, one
association with the declared Nonconformity. Repeated failing instances with
the same Nonconformity and the same selectable IRV leaf are evidence of that
single pending entry, not additional pending entries. Preserve and aggregate
their traceable evidence for a minimal DESCRIPTION when needed. This rule shall
never merge distinct Nonconformities or distinct selectable IRV leaves.

When a triggered Nonconformity has no declared IRV projection, preserve its
FAIL and route the missing operational projection to the report's human
treatment section. Do not invent an e-SCI item or cause and do not convert the
FAIL to MANUAL_REVIEW.

For DESCRIPTION_POLICY MINIMAL_IF_NEEDED, attach a DESCRIPTION only when a
concrete fact already present in the consolidated result and its evidence is
needed to identify the divergence. Simple documentary absence requires no
additional description. DESCRIPTION shall normally contain one sentence of no
more than 180 characters; 180 is a preference, not a validity limit. The
absolute limit is 500 characters. DESCRIPTION shall not reproduce the complete
IRV_CAUSE, IRV_SUBCAUSE or IRV_CRITERION. If no description is needed,
project exactly "Não necessário." for report rendering.

Derive candidate technical counters only from the canonical consolidated
result set before rendering. Validate:

VERIFICATIONS_EXECUTED counts only result records with
result_origin=EVALUATED:
PASS + FAIL + NOT_APPLICABLE + MANUAL_REVIEW.
PROPAGATED records are counted separately as VERIFICATIONS_PROPAGATED and do
not enter VERIFICATIONS_EXECUTED.

If the equality is not satisfied, record REPORT_COUNTER_INCONSISTENCY as an
audit-only diagnostic and omit the invalid technical totals. Never fabricate,
adjust or reconstruct a counter from rendered text blocks. The inconsistency
shall not create or modify PASS, FAIL, NOT_APPLICABLE, MANUAL_REVIEW,
Nonconformities or operational pending entries. Continue operational report
generation when the canonical results and operational projection remain
intact; expose the inconsistency explicitly only in audit mode.

The transient operational projection becomes immutable before Phase 7.

END PHASE 6A.
