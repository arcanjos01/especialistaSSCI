###############################################################################
# PHASE 4B
# REQUIREMENT APPLICABILITY RESOLUTION
###############################################################################

Only after Phase 4A completes, resolve the declared applicability of every
Requirement candidate against immutable Process Memory. Preserve the existing
SMSCI and IN19 selection rules before applying the alteration-scope rules.

After an explicit positive SMSCI_IEL decision, resolve exactly one internal
IN19_DOCUMENTATION_REGIME from only the REQUEST_DATE extracted from the
selected comprovante: REQUEST_DATE <= 2024-04-24 is LEGACY; REQUEST_DATE >
2024-04-24 is CURRENT; absent, unverified or not safely comparable REQUEST_DATE
is UNRESOLVED. Do not use PPCI, ART/RRT/TRT, atestado, previsão, início,
conclusion date or textual mention of obra nova. SMSCI_IEL negative preserves
the declared IN19 applicability-review path and does not resolve a regime.

Produce one closed REQUIREMENT_APPLICABILITY_DECISIONS ledger. A decision key
is (REQUIREMENT) for a non-iterative Requirement and
(REQUIREMENT, BINDING_SMSCI) for each positive official target of
REQ_T1_DRT_SMSCI / T1_DRT_SMSCI_COVERAGE. If WORKLIST.SMSCI is empty, preserve
REQ_T1_DRT_SMSCI's existing general Requirement selection with exactly one
(REQUIREMENT) APPLICABLE base decision and no BINDING_SMSCI. It creates no
SMSCI incidence and preserves the existing Criterion unit with an empty
ITERATION_DOMAIN. Every decision contains REQUIREMENT, optional BINDING_SMSCI,
RULE_ID, exactly one DECISION from APPLICABLE, NOT_APPLICABLE or
APPLICABILITY_REVIEW_REQUIRED, PROCESS_MEMORY_FACT_REFERENCES,
RDE_RECORD_REFERENCES, SOURCE_DOCUMENT_REFERENCES and BASE_RATIONALE. A review
decision also freezes the mapped HUMAN_TREATMENT_OBLIGATION and
HUMAN_TREATMENT_REASON, resolved SMSCI name, and documented area when available.
If no individualized source reference exists, record that fact explicitly. All
reference fields and the rationale are copied from already closed Process
Memory and the applicable Base rule; no source is reopened.

The ledger's candidate key domain is closed by the declared Requirement
metadata, applicable target class, completed Phase 4A decisions and, for IN19,
the resolved regime. Each candidate key appears exactly once. The three
outcome sets APPLICABLE_INCIDENCES, NOT_APPLICABLE_INCIDENCES and
APPLICABILITY_REVIEW_REQUIRED are pairwise disjoint and their union equals the
closed candidate key domain. No incidence may be omitted, duplicated or placed
in more than one set. APPLICABLE_REQUIREMENTS is the unique Requirement
projection of APPLICABLE_INCIDENCES, including the Requirement-level base
decision for the empty RT-003 iteration domain. A Requirement may have both
applicable and review incidences only when distinct SMSCI bindings have those
respective outcomes; that does not duplicate or rewrite the normative
Requirement.

Requirements without SMSCI metadata retain their declared applicability
semantics and shall not be filtered through PROCESS.SMSCI. For Requirements
with SMSCI metadata, an absent target from a complete Phase 4A resolution is
NOT_APPLICABLE under that declared metadata rule. The derived internal
SMSCI_IN19_APPLICABILITY_REVIEW and IN19_DOCUMENTATION_REGIME continue to follow
their existing rules and do not participate in alteration-scope decisions.

WORKLIST.SMSCI remains the global positive projection for
REQ_T1_DRT_SMSCI: every and only positive OFFICIAL_ESCI_SCOPE target in
PROCESS.SMSCI, excluding derived internal targets such as SMSCI_SDAI and
SMSCI_IN19_APPLICABILITY_REVIEW. It is immutable and is never reduced by an
alteration document. Create a separate ordered WORKLIST.SMSCI_EXECUTION from
those bindings whose canonical decision key
(REQ_T1_DRT_SMSCI, BINDING_SMSCI) is APPLICABLE. If WORKLIST.SMSCI is empty,
the Requirement-level base decision selects the existing T1 Criterion unit
with an empty ITERATION_DOMAIN; it adds no binding to either worklist. This
execution subset is not PROCESS.SMSCI, does not replace WORKLIST.SMSCI and
never discovers an SMSCI.

For an explicitly identified alteration, apply the following rule to each
positive SMSCI binding of REQ_T1_DRT_SMSCI independently:

- EXECUTED_IN_INTERVENTION, MODIFIED_OR_RESIZED or
  PREEXISTING_SYSTEM_AFFECTED yields APPLICABLE when the complete per-system
  statement and its provenance are available. The RT-003 binding remains in
  WORKLIST.SMSCI_EXECUTION.
- PREEXISTING_SYSTEM_DECLARED_UNCHANGED yields NOT_APPLICABLE only when the
  cumulative proof gate below is fully satisfied for that exact SMSCI and area.
- An absent, silent, generic, component-only, ambiguous or conflicting relation,
  an incomplete proof gate, or an unusable RDE/Process Memory reference yields
  APPLICABILITY_REVIEW_REQUIRED for that binding. Never convert uncertainty to
  NOT_APPLICABLE or FAIL.

The cumulative proof gate for NOT_APPLICABLE requires all of the following to
match through explicit identifiers and traceable records: (1) a formal
complementary PPCI with a unique PPCI_IDENTIFIER and documentally verified
PPCI_APPROVAL_STATUS=APPROVED; (2) its explicit
PREVIOUS_ATTESTADO_PROTOCOL_IDENTIFIER matches exactly one presented
ATESTADO_DE_CONSTRUCAO PROTOCOL_IDENTIFIER; (3) the exact official SMSCI code
and individual AREA_IDENTIFIER occur in a per-system scope statement contained
in that same approved complementary PPCI and identify the preexisting system as
outside the intervention's design/installation scope; and (4) a signed
PPCI_ALTERATION_TECHNICAL_REPORT explicitly identifies the same PPCI, prior
certificate, official SMSCI and area, corroborates that the system was neither
executed nor affected, and does not conflict with the approved PPCI scope.
Any signed, traceable DRT or technical report for the same SMSCI and area that
indicates execution, modification, redimensioning or impact is a conflict and
forces APPLICABILITY_REVIEW_REQUIRED. A DRT or laudo alone, an explanatory
letter, silence, a generic statement, document existence, absence of DRT,
area arithmetic, or absence from a scope list never proves NOT_APPLICABLE.
Every required fact, record, source document, approval, identity, area and
scope reference must be present and unambiguous; otherwise route only that
incidence to review.

For the Table 4 Requirements named PENDENTE in the Fase 2 matrix, preserve the
existing global selection when no formal alteration marker exists. During a
formal alteration, a complete, individually traceable positive
execution/modification/affected relation for that Requirement's single
declared SMSCI yields APPLICABLE. Silence, generic or ambiguous text, a
declaration that the system is unchanged, missing facts, an incomplete proof or
conflicting evidence yields APPLICABILITY_REVIEW_REQUIRED by Requirement. The
cumulative proof gate above is specific to REQ_T1_DRT_SMSCI and shall not be
reused by analogy to produce NOT_APPLICABLE for a Table 4 document obligation.
This Fase 2 matrix authorizes no Requirement-specific Table 4 exclusion;
NOT_APPLICABLE for a positive global target requires its own declared,
Requirement-specific rule and normative basis. Do not create a separate Table 4
decision per SMSCI or filter Table 4 as a block. Requirements designated
PRESERVAR in the matrix remain APPLICABLE whenever their existing global
target/regime rule selects them, including REQ_IN08_ESTANQUEIDADE,
REQ_IN09_TEST_REPORT, REQ_IN15_COMMISSIONING, REQ_IN18_CMAR and
REQ_IN19_LEGACY_DOCUMENTATION. Preserve all other Table 4 and IN19 regime
selection semantics; this alteration rule does not resolve or reuse
REQ_IN19_REGIME_REVIEW.

Requirements selected by another existing internal derivation retain that
semantics. No Requirement, Criterion, Nonconformity or SMSCI may be created or
rewritten.

END PHASE 4B.

# PHASE 4C
# PLAN MATERIALIZATION
###############################################################################

INPUT: the frozen REQUIREMENT_APPLICABILITY_DECISIONS ledger,
APPLICABLE_REQUIREMENTS and the release-derived COMPILED_EXECUTION_INDEX.
Consume these inputs only; do not recalculate, reinterpret or modify
Applicability or IN19_DOCUMENTATION_REGIME.

Materialize the ordered, closed and immutable PLANNED_EXECUTION_UNITS as a
local procedure:

1. For each Requirement with at least one APPLICABLE incidence or an
   APPLICABLE Requirement-level base decision, in its resolved order, find its
   block in COMPILED_EXECUTION_INDEX and copy every listed
   UNIT_KEY in that block order. UNIT_KEY shall be copied literally. Do not
   generate, rename, summarize or reinterpret it. Semantic labels are not valid
   substitutes. A Requirement with only NOT_APPLICABLE or
   APPLICABILITY_REVIEW_REQUIRED decisions produces no planned unit, except the
   RT-003 empty-domain base selection declared in Phase 4B.

2. Preserve the declared TABLE, CONTEXT and every VALIDATE associated with the
   copied Requirement and Criterion. APPLIES_TO shall be consistent with the
   completely resolved PROCESS.SMSCI; any inconsistency stops execution before
   the Engine.

3. When the Requirement block declares ITERATION_SOURCE, materialize one unit
   per listed UNIT_KEY, with ITERATION_DOMAIN resolved and frozen from the
   ordered APPLICABLE incidence bindings for that Requirement. For the RT-003
   empty-domain base selection, preserve an empty ITERATION_DOMAIN. For
   REQ_T1_DRT_SMSCI / T1_DRT_SMSCI_COVERAGE, ITERATION_DOMAIN equals
   WORKLIST.SMSCI_EXECUTION and must be an ordered subset of WORKLIST.SMSCI.
   Review or NOT_APPLICABLE bindings are never planned or passed to the
   Criterion. Do not materialize a UNIT_KEY per binding.

4. Validate the existing Criterion and Nonconformity references without
   creating or triggering a Nonconformity. Do not execute a Criterion while
   constructing the plan.

5. Freeze PLANNED_EXECUTION_UNITS. Compare its ordered UNIT_KEY sequence for
   exact equality with the ordered sequence selected from
   COMPILED_EXECUTION_INDEX for Requirements with APPLICABLE incidences or an
   APPLICABLE Requirement-level base decision. For every iterative unit also
   compare planned_bindings exactly with the ordered
   APPLICABLE binding set. Any order change, absence, extra key, binding,
   duplicate or mismatch is EXECUTION_INTEGRITY_ERROR: STOP BEFORE EXECUTION.

Each PLANNED_EXECUTION_UNIT contains its literal UNIT_KEY, frozen
ITERATION_DOMAIN when applicable, and a reference to the corresponding
applicability decision; the empty RT-003 domain references its Requirement-level
base decision. It contains no documentary evidence copied from
Process Memory, execution result or anticipated Nonconformity.

ITERATION_DOMAIN defines the complete planned_bindings set. FOR_EACH remains
internal to the Criterion and preserves aggregate result semantics. In
particular, T1_DRT_SMSCI_COVERAGE remains one planned unit and one aggregate
result over only its APPLICABLE bindings; it may produce at most one NC_T1_002
when its declared Criterion result is FAIL. APPLICABILITY_REVIEW_REQUIRED is a
separate Phase 4B decision; it is not a Criterion result, MANUAL_REVIEW,
UNKNOWN, FAIL, Nonconformity or planned binding. A mixed Requirement preserves
its applicable bindings in the Criterion and carries only its other incidences
to human treatment.

No list parallel to PLANNED_EXECUTION_UNITS shall be introduced merely to
duplicate its expected, selected or executed Criteria.

END PHASE 4C.

before the results are consolidated or projected.

FAIL

NOT_APPLICABLE

MANUAL_REVIEW

###############################################################################
# PHASE 6
# RESULT CONSOLIDATION
###############################################################################

Before consolidation or projection, verify the Plan-to-Results invariant:

- every PLANNED_EXECUTION_UNITS UNIT_KEY produced exactly one result;
- no UNIT_KEY produced two or more results;
- no result exists without a UNIT_KEY in PLANNED_EXECUTION_UNITS;
- for every iterative Criterion, evaluated_bindings equals planned_bindings.

If any of these checks fails, stop execution with EXECUTION_INTEGRITY_ERROR.

EXECUTION_INTEGRITY_ERROR is an internal execution error only. It is not a
normative result and shall never be treated as:

PASS, FAIL, NOT_APPLICABLE, MANUAL_REVIEW, UNKNOWN or Nonconformity.

On EXECUTION_INTEGRITY_ERROR:

- stop before IRV/e-SCI projection;
- do not generate a pendency;
- do not alter normative results;
- do not convert the error to MANUAL_REVIEW;
- expose it only through the existing audit/debug channel when supported by the
  architecture;
- do not trigger Report Generation or IRV/e-SCI projection.

Consolidate all Criterion results.

Associate Nonconformities only with FAIL results.

Criterion results shall remain immutable after consolidation.

Associate operational alerts only with MANUAL_REVIEW results.

APPLICABILITY_REVIEW_REQUIRED incidences remain frozen Phase 4B decisions;
they are not MANUAL_REVIEW results or Operational Alerts and do not affect
Criterion counts, Nonconformities or e-SCI projection. Their predeclared
HUMAN_TREATMENT_OBLIGATION and HUMAN_TREATMENT_REASON, resolved SMSCI name,
documented area and source references/locations may be projected to operational
TRATAMENTO HUMANO as specified in 06_reports; do not draft or infer new text.

Operational Alerts are internal execution artifacts.

Before Report Generation,

every Operational Alert shall be translated into exactly one
MANUAL_REVIEW report entry.

Operational Alert identifiers shall never appear in user-visible reports.

MANUAL_REVIEW results shall never generate Nonconformities.

MANUAL_REVIEW shall propagate to every dependent Criterion unless an explicit documentary rule defines otherwise.

Do not modify previous results.

No report section shall be generated before Result Consolidation completes.

###############################################################################
# PHASE 6A
# IRV OPERATIONAL PROJECTION
###############################################################################

Only after Result Consolidation completes, consume the immutable consolidated
Criterion results and their declared Nonconformity associations.

For each consolidated FAIL associated with a Nonconformity that declares
IRV_TABLE, IRV_CRITERION and IRV_CAUSE in 05_nonconformities, create exactly
one transient operational pending-entry. Load IRV_SUBCAUSE only when declared;
the selectable leaf is IRV_SUBCAUSE when present, otherwise IRV_CAUSE. Preserve
IRV_CAUSE as the internal parent when a subcause is present. Preserve consolidated result order and the complete traceability of the source
FAIL and documentary evidence.

The operational projection is not a Criterion result, a Nonconformity or
documentary evidence. It shall never:

- create, remove, merge or modify a FAIL;
- create or modify a Nonconformity;
- execute a Requirement or Criterion;
- recalculate Applicability or PROCESS.SMSCI;
- reopen a Source Document or the RDE;
- infer an IRV item, cause or subcause by similarity;
- create an artificial IRV_SUBCAUSE.

Do not group, deduplicate or suppress pending entries because they share the
same IRV_CRITERION. Distinct selectable leaves — IRV_SUBCAUSE when declared,
otherwise IRV_CAUSE — shall remain distinct operational pending entries.

FOR_EACH is a structural aggregation inside one Criterion evaluation. Its
instances shall produce one consolidated Criterion result and, on FAIL, one
association with the declared Nonconformity. Repeated failing instances with
the same Nonconformity and the same selectable IRV leaf are evidence of that
single pending entry, not additional pending entries. Preserve and aggregate
their traceable evidence for a minimal DESCRIPTION when needed. This rule shall
never merge distinct Nonconformities or distinct selectable IRV leaves.

When a triggered Nonconformity has no declared IRV projection, preserve its
FAIL and route the missing operational projection to the report's human
treatment section. Do not invent an e-SCI item or cause and do not convert the
FAIL to MANUAL_REVIEW.

For DESCRIPTION_POLICY MINIMAL_IF_NEEDED, attach a DESCRIPTION only when a
concrete fact already present in the consolidated result and its evidence is
needed to identify the divergence. Simple documentary absence requires no
additional description. DESCRIPTION shall normally contain one sentence of no
more than 180 characters; 180 is a preference, not a validity limit. The
absolute limit is 500 characters. DESCRIPTION shall not reproduce the complete
IRV_CAUSE, IRV_SUBCAUSE or IRV_CRITERION. If no description is needed,
project exactly "Não necessário." for report rendering.

Derive candidate technical counters only from the canonical consolidated
result set before rendering. Validate:

VERIFICATIONS_EXECUTED = PASS + FAIL + NOT_APPLICABLE + MANUAL_REVIEW

If the equality is not satisfied, record REPORT_COUNTER_INCONSISTENCY as an
audit-only diagnostic and omit the invalid technical totals. Never fabricate,
adjust or reconstruct a counter from rendered text blocks. The inconsistency
shall not create or modify PASS, FAIL, NOT_APPLICABLE, MANUAL_REVIEW,
Nonconformities or operational pending entries. Continue operational report
generation when the canonical results and operational projection remain
intact; expose the inconsistency explicitly only in audit mode.

The transient operational projection becomes immutable before Phase 7.

END PHASE 6A.

# PHASE 7
# REPORT GENERATION
###############################################################################

Generate the operational report using only the immutable consolidated results,
the immutable Phase 6A operational projection, the frozen
APPLICABILITY_REVIEW_REQUIRED incidence set from Phase 4B and 06_reports.
Project only the frozen HUMAN_TREATMENT_OBLIGATION,
HUMAN_TREATMENT_REASON, resolved SMSCI name, documented area and source
references/locations into TRATAMENTO HUMANO. If references are absent, report
that fact without completing them. Do not draft or infer text, reopen a source
or reinterpret the incidence as an execution result.

Do not expose Requirements, Criteria or internal identifiers in the
operational report.

The operational report shall not reinterpret execution results.

If the user explicitly requests any Technical Annex trigger declared by
06_reports, append the Technical Annex defined by that same document.

The Technical Annex shall describe only the execution actually performed by the inference engine.

The audit report shall not introduce new documentary findings after Result Consolidation.

# EXECUTION RULES
###############################################################################

Never execute phases out of order.

Never return to a previous phase.

Never modify results produced in previous phases.

Never replace documentary evidence with model knowledge.

Never infer absent information.

Informação insuficiente para verificar.

The report generation phase shall never trigger additional documentary analysis.

If additional documentary evidence would be required to change a result, the execution shall terminate with the previously consolidated results.
