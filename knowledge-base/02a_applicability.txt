PURPOSE

This document defines the productive applicability-resolution boundary for
SMSCI-scoped Requirements and Criteria. PROCESS.SMSCI is exclusively the output
of Phase 4A. It is never an extracted fact and shall not be created by the
Engine, a Requirement, a Criterion or a Report.

INPUT AND OUTPUT

Applicability Resolution consumes only complete, immutable Process Memory,
the canonical entities of 01_entities and the declared rules below. After the
official source completeness guard succeeds, it releases PROCESS.SMSCI,
APPLICABLE_REQUIREMENTS and SELECTED_CRITERIA, plus
IN19_DOCUMENTATION_REGIME only when SMSCI_IEL is positive. When explicit,
traceable alteration statements exist in Process Memory, preserve
DECLARED_INTERVENTION_SMSCI_RELATIONS as a separate factual view. This view is
not an SMSCI, applicability decision, Requirement, Criterion or result, and its
absence does not add a completeness condition. PROCESS.SMSCI shall never be
emitted partially. IN19_DOCUMENTATION_REGIME is an internal
applicability-selection value, never an SMSCI, documentary fact, Requirement,
Criterion or result.

PROCESS.SMSCI is the global official PPCI/e-SCI scope established by the
selected comprovante. It remains unchanged by alteration documents.
DECLARED_INTERVENTION_SMSCI_RELATIONS is a separate, traceable view built only from
individualized documentary statements declared under
PPCI_ALTERATION_SMSCI_STATEMENT in 01_entities. It records how a stated SMSCI
relates to the intervention; it neither creates an SMSCI nor replaces or
subtracts from PROCESS.SMSCI. Silence creates no relation record and is not a
negative decision. A generic statement about "the other systems" is never
expanded into per-system relations.

ARCHITECTURAL_BLOCKER is a stop condition before the Engine, not an output
state or Criterion result. It does not authorize NOT_APPLICABLE,
MANUAL_REVIEW, UNKNOWN or FAIL.

PRODUCTIVE AUTHORIZED SOURCE SCOPE

The exclusive productive source is exactly one document with:

- DOCUMENT TYPE COMPROVANTE_DE_SOLICITACAO_DE_HABITESE, whose presented
  document type is exactly "COMPROVANTE DE SOLICITAÇÃO DE HABITE-SE";
- a deterministic documentary match to the current request;
- the section SISTEMAS_E_MEDIDAS_DE_SEGURANCA; and
- a complete, legible and verifiable structural representation of that section.

Select exactly one comprovante for the current request using only documentary
REQUEST_IDENTIFIER, PROCESS_IDENTIFIER and PROTOCOL_IDENTIFIER facts already
present in immutable Process Memory. PROCESS_IDENTIFIER identifies only the
process or building shared between returns and shall never select the current
comprovante by itself. A candidate shall have a comparable and equal
PROTOCOL_IDENTIFIER or REQUEST_IDENTIFIER that documentally identifies the
current request unambiguously, with no different value for any other strong
identifier available on both sides. Conflicting strong identifiers are an
ARCHITECTURAL_BLOCKER. When PROCESS_IDENTIFIER is available on both sides of a
strongly matched document, its values shall also be equal; otherwise that
document is not a candidate. A document matching only by PROCESS_IDENTIFIER is
not a candidate and does not compete with exactly one strong candidate. If no
strong candidate remains or more than one strong candidate remains, selection
is indeterminate and shall block. A previous return that shares a process
identifier but is documentally identified by different request and protocol
identifiers is not the current candidate. Filename, newest date and
attachment order shall never select a
document. No unique matching document, contradictory identifiers within the
selected record, an absent document, an absent section, an incomplete section,
an illegible section, an unverifiable section, an unknown code or incomplete
traceability is an ARCHITECTURAL_BLOCKER before the Engine and before partial
PROCESS.SMSCI.

The minimal RDE schema already declared in 01_entities is sufficient for this
source: the comprovante REQUEST_DATE and identifiers; section facts
STRUCTURALLY_COMPLETE, LEGIBLE and VERIFIABLE; and item facts
OFFICIAL_ESCI_CODE, PRESENTED_SYSTEM_MEASURE_DESCRIPTION,
RPCI_ORIENTATIVE_TEXT and SOURCE_LOCATION. source_document remains required by
Documento 09-RDE; this document does not alter that specification.

RULE CONTRACT

Every productive rule declares its target, authorized document and section,
exact Process Memory fact, deterministic condition and traceability equivalent
to Applicability Rule -> Process Memory fact -> RDE record -> Source Document.
An explicit negative decision requires the same complete trace. The absence of
a positive trigger outside the complete authorized section is never a negative
decision.

DERIVED RULE: SMSCI_SDAI

After all official decisions are complete, preserve SMSCI_AI and SMSCI_DAI as
separate official facts and decisions. If SMSCI_AI is positive OR SMSCI_DAI is
positive, include SMSCI_SDAI as the explicit derived internal requirement scope.
If both are negative, record the explicit derived negative decision for
SMSCI_SDAI. This derived scope activates the existing IN12 Requirement/Criterion
metadata only; it does not create a Requirement, Criterion or Nonconformity.

Declared foundation: IRV Tabela 4 item IN12; IN12/2024 art. 1, definition in
art. 4 XII, and art. 47. No area, height or GLP rule is authorized here.

DERIVED RULE: SMSCI_IN19_APPLICABILITY_REVIEW

After all official decisions are complete, preserve SMSCI_IEL as the separate
official fact and decision. If SMSCI_IEL is positive, record the explicit
derived negative decision for SMSCI_IN19_APPLICABILITY_REVIEW. If SMSCI_IEL is
negative because the selected section is complete, legible and verifiable,
include SMSCI_IN19_APPLICABILITY_REVIEW as the explicit derived internal
requirement scope and record its positive decision with the same traceability.
This derived scope selects only the IN19 applicability manual-review
Requirement/Criterion. It does not represent an SMSCI registered in the
PPCI/e-SCI, does not create SMSCI_IEL, does not establish that IN19 applies or
is dispensed, and does not create a Requirement, Criterion or Nonconformity.

No occupation, area, height, population, risk, construction date, transitional
rule or other external applicability rule is authorized by this derivation.

PPCI ALTERATION DOCUMENT FACTS AND INTERVENTION RELATIONS

The optional PPCI alteration explanation is a supplemental documentary source,
not a required document. If present, extract only its explicit, traceable facts
using the entities in 01_entities. The interaction gate in instruções_gem.txt
is outside normative applicability; a user's response that no explanation
exists is not RDE, Process Memory evidence or an applicability input.

An alteration marker is available only from an explicit service/protocol type,
an explicit PPCI submission class, an explicitly declared alteration type, or
a safely verifiable positive ADDED_AREA_M2. Do not infer the marker from
filename, area previously approved, an isolated vague use of "alteration" or
a textual mention that does not describe the requested intervention.

For each explicit PPCI_ALTERATION_SMSCI_STATEMENT, resolve a relation only
when OFFICIAL_ESCI_CODE is an exact official code or SMSCI_REFERENCE_TEXT
unambiguously identifies one complete canonical SMSCI by its canonical name
or a name/alias that denotes the complete system, and the same statement
explicitly supports one declared INTERVENTION_RELATION. A component alias is
not a whole-system identifier: CENTRAL_GLP alone does not identify all of
SMSCI_GAS, and HIDRANTE, HIDRANTES or REDE_DE_HIDRANTES alone do not identify
all of SMSCI_SHP. If no complete system target is resolved, do not create a
PPCI_ALTERATION_SMSCI_STATEMENT record; preserve its wording and source
location only in ALTERATION_DESCRIPTION and SOURCE_LOCATION of
PPCI_ALTERATION_EXPLANATION. A statement for a resolved target outside
PROCESS.SMSCI cannot add that target to PROCESS.SMSCI or activate a
Requirement. Conflicts, ambiguous references, generic declarations and
unmentioned systems do not yield a per-system positive or negative relation.
An explicit PREEXISTING_SYSTEM_DECLARED_UNCHANGED is a documentary statement,
not a conformity finding and not, by itself, permission to suppress a
Requirement.

ARTICLE 98: DOCUMENTED SCOPE FOUNDATION AND CURRENT LIMIT

IN 1, part 1, art. 98 distinguishes an expansion that does not compromise or
require redimensioning SMSCI from one that affects or requires updating
systems. Its caput also requires a complementary PPCI tied to a previously
granted construction certificate. Paragraph 1, I limits technical
responsibility in that case to the altered area and SMSCI effectively designed
and installed there; paragraph 2 addresses the affected-system case. This is
not a blanket exemption for prior systems.

The current documentary schema can preserve an explicit construction
certificate, PPCI classification, area facts and individual statements in an
alteration explanation. It does not establish that an explanation or a
responsible technician's statement is itself approved technical evidence that
an existing system was actually unaffected. It also does not yet relate an
approved complementary PPCI's technically verified design, the added area
and each system's design/installation scope with a deterministic contract.
Therefore this release records DECLARED_INTERVENTION_SMSCI_RELATIONS as
documentary facts for traceable human consideration but does not use them
alone to remove a positive global SMSCI from WORKLIST.SMSCI or
APPLICABLE_REQUIREMENTS. Prior area approval is never evidence of the
construction certificate.

Current Table 1 DRT worklist and Table 4 Requirements retain their declared
global behavior. In particular, a system explicitly described as unmodified
in an explanatory letter remains in PROCESS.SMSCI, its DRT iteration and
Table 4 selection in this release. Do not create a Requirement, Criterion,
Nonconformity, FAIL, NOT_APPLICABLE or manual-review result from this
insufficient scope evidence. A future Requirement-specific rule requires
sufficient authorized technical evidence and its own normative basis.

PHASE 4A: COMPLETENESS GUARD

Resolve exactly the 28 OFFICIAL_ESCI_SCOPE targets through the catalog. Before
the Engine, any source-selection ambiguity, documentary insufficiency, unknown
code, conflict, missing decision or incomplete traceability raises
ARCHITECTURAL_BLOCKER. No PROCESS.SMSCI is released until all 28 official
positive/negative decisions and the declared SDAI derivation are complete.
The declared IN19 applicability-review derivation is completed only after that
same guard succeeds; an ARCHITECTURAL_BLOCKER shall never be converted to its
manual review.

PHASE 4B: REQUIREMENT APPLICABILITY RESOLUTION

Requirements without SMSCI metadata retain their declared applicability
semantics. Requirements with SMSCI metadata are applicable only after complete
Phase 4A when their target is in PROCESS.SMSCI. Iterative Requirements retain
their declared form; no Requirement is created or rewritten.

IN19 DOCUMENTATION REGIME RESOLUTION

Only after the explicit positive SMSCI_IEL decision, resolve exactly one
internal IN19_DOCUMENTATION_REGIME before selecting any IN19 Requirement:

- REQUEST_DATE documentally extracted from the selected comprovante, in a
  complete, legible, verifiable and safely comparable DATE representation, is
  less than or equal to 2024-04-24: LEGACY;
- the same REQUEST_DATE greater than 2024-04-24: CURRENT;
- absent, incomplete, illegible, unverifiable or not safely comparable
  REQUEST_DATE: UNRESOLVED.

The only authorized automatic input is the selected comprovante REQUEST_DATE.
Do not use PPCI, ART/RRT/TRT, atestado, previsão, início, conclusion date,
textual mention of obra nova or any other document or date. This resolution
does not change the selected document, PROCESS.SMSCI, WORKLIST.SMSCI or the
official SMSCI_IEL decision. When SMSCI_IEL is negative, do not resolve an
IN19_DOCUMENTATION_REGIME and preserve the declared IN19 applicability-review
path.

For a positive SMSCI_IEL decision, select IN19 Requirements only by their
declared IN19_DOCUMENTATION_REGIME in addition to their SMSCI metadata:

- CURRENT selects only REQ_IN19_EXECUTION, REQ_IN19_GROUNDING and
  REQ_IN19_FINAL_VERIFICATION;
- LEGACY selects only REQ_IN19_LEGACY_DOCUMENTATION;
- UNRESOLVED selects only REQ_IN19_REGIME_REVIEW.

No IN19 Requirement declared for another regime is applicable. A regime is not
derived from a Criterion result, including UNKNOWN. The required chain is
SMSCI_IEL -> IN19_DOCUMENTATION_REGIME -> APPLICABLE_REQUIREMENTS ->
COMPILED_EXECUTION_INDEX -> PLANNED_EXECUTION_UNITS.

WORKLIST.SMSCI

WORKLIST.SMSCI is a transient subset of PROCESS.SMSCI. For exactly
REQ_T1_DRT_SMSCI / T1_DRT_SMSCI_COVERAGE, it contains every and only official
positive OFFICIAL_ESCI_SCOPE target in PROCESS.SMSCI. It excludes derived
internal requirement scopes, including SMSCI_SDAI and
SMSCI_IN19_APPLICABILITY_REVIEW, so AI/DAI are not duplicated by the SDAI
derivation and the IN19 applicability review has no iterative DRT unit. This is
not a general architectural identity. Declared intervention relations do not
change this worklist in this release.

PHASE 4C: CRITERION SELECTION

Select Criteria exclusively through declared USES/REQUIREMENT associations of
applicable Requirements, preserving TABLE, CONTEXT and order. APPLIES_TO must
be consistent with complete PROCESS.SMSCI; an inconsistency blocks execution.
No Criterion is created or selected by alias, document, similarity or text.

TRACEABILITY

Source Document -> RDE -> Process Memory -> Applicability Rule ->
PROCESS.SMSCI -> IN19_DOCUMENTATION_REGIME when applicable -> Requirement ->
Criterion -> Result -> Nonconformity when applicable.

For general Requirements, Applicability Rule and PROCESS.SMSCI are not
artificially required; preserve their existing documentary traceability and
declared metadata.

runtime. It does not prohibit the explicit, authorized documentary schema
declared in 01_entities by this Knowledge Base evolution.
